# Borrow the technique, credit the source

This repository is an original synthesis of visual-documentation preferences and the sources below. It does not bundle their code, skills, screenshots, or logos. These are useful references, not a measured ranking of teaching effectiveness. Public pages were checked on October 22, 2026.

| Source | What to borrow | What not to infer |
| --- | --- | --- |
| [Andrej Karpathy · micrograd trace notebook](https://github.com/karpathy/micrograd/blob/master/trace_graph.ipynb) | A tiny computation with visible inputs, operations, values, and gradients | The notebook uses Graphviz; this is not evidence that Karpathy uses GSAP or endorses this skill |
| [Bret Victor · Learnable Programming](https://worrydream.com/LearnableProgramming/) | Make state and execution inspectable | Interaction alone does not establish understanding |
| [Simon Willison · Interactive explanations](https://simonwillison.net/guides/agentic-engineering-patterns/interactive-explanations/) | Turn the confusing hidden operation into an observable process | A general code walkthrough may still leave the mechanism unclear |
| [Amit Patel · Introduction to A*](https://www.redblobgames.com/pathfinding/a-star/introduction.html) | Reuse a concrete example while introducing one idea at a time | The visual world and the algorithm's graph are different representations |
| [Mike Bostock · Visualizing Algorithms](https://bost.ocks.org/mike/algorithms/) | Choose intermediate states or outputs according to the question | Animation is one option, not the default answer |
| [Wattenberg, Viégas & Johnson · How to Use t-SNE Effectively](https://distill.pub/2016/misread-tsne/) | Use counterexamples and controlled comparisons to show a visual's limits | A persuasive picture is not proof of its interpretation |
| [Jason Zhou · How to Design With AI](https://superdesign.dev/blog/how-to-design-with-ai) | Give a purpose and specific references, then refine individual components | The article promotes the author's Superdesign product; this repo does not require it |
| [Paul Bakaus · Impeccable](https://github.com/pbakaus/impeccable) | Deliberate hierarchy, refinement, and visual inspection | Design polish does not establish factual accuracy; its entire orchestration workflow is not adopted |
| [Derek Schwede · html-explainer](https://github.com/ds-vibe/html-explainer) | Portable HTML explanation and rendered quality checks | This repo does not require a fixed interview or demo count |
| [Rebecca Fordon · teaching-explainer](https://github.com/rlfordon/teaching-explainer) | Concrete instructional examples and purposeful learner feedback | Reference documentation does not always need a lesson or quiz |

## The preference that ties it together

A useful visual is a compact argument: this record enters here, this rule changes it, this team owns the handoff, and this result follows. Consistent type and recognizable system identities help the reader follow that argument. They do not replace source investigation.

Keep the main picture readable without a click. Keep a disclosure when it reveals a useful rule or example. Remove the ones that hide the explanation or repeat it in prose.
